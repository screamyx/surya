## Rig

Two rig facts that shape every row below. Neither is a product defect.

1. The `windows-dtry` MCP returns `No windows found` and `No active window found`
   for every window on dtry, on every call, while its `Screenshot` and its input
   injection both work.
   So `App mode=switch`, `App mode=resize`, `WaitFor` on a window name and every
   label-based `Click` are unusable in this session.
   Input and window control run instead through a `schtasks /it` task in session 1
   (`surya-e2e2-run`) driving `SendInput`, and frames are taken with `BitBlt` of
   the app's client rectangle after the window is brought to the front.
2. I use `ssh dtry` to move frames off the box, to read
   `E:\surya-e2e2-data\logs\surya-headed.log`, and to read
   `E:\surya-e2e2-data\ui-settings.json`.
   The MCP cannot reach files. The brief allows this and asks that it be said here.

A third rig note, recorded because it wasted time and would waste anyone else's.
`MoveWindow` and `SetWindowPos` against the surya window always force the height
to 1460 px, whatever height is asked for, while honouring the width.
A mouse drag on the same window edge resizes it correctly to any size down to the
minimum. So programmatic resize is not a usable measurement and every size in this
record was set by dragging the window border with injected mouse input.

### E2E-ENGINE-01 (bug) - the app re-subscribes to Browser.Watch every two seconds, all session long

Found in the engine log while the desktop was handed to another seat, not by
looking for it.

- expected: the app attaches to `Browser.Watch` once and holds it.
- seen: the engine logged `browser broker: a new app pane replaced the previous one` **1,690 times in 62 minutes**, one every ~2.2 seconds.

The window matches my app's connection exactly. First line
`2026-09-06T12:30:42.914418Z`, and my app dialled the engine at
`12:30:42.145252Z`. Last line `2026-09-06T13:32:47.886762Z`, and the engine
logged `rpc: connection closed peer=100.113.128.91:58576` at `13:32:47.139085Z`.
No further lines appeared in the five seconds after that. One client, one hour,
227 KB of engine log.

The engine only prints that line when a watcher was already registered
(`crates/engine/src/browser_rpc.rs:172-180`: `s.watcher.replace(tx).is_some()`),
so the app is displacing its own previous subscription each time. The client
loop is `crates/ui/src/browser_agent.rs:69-137`: subscribe to
`methods::BROWSER_WATCH`, drain until the stream ends, then
`cx.background_executor().timer(RETRY).await` and subscribe again, with
`RETRY = Duration::from_secs(2)` at line 25. The measured 2.2 s cadence matches
that constant.

What I did not establish: why the subscription stream ends on every pass. The
`println!` diagnostics in that loop (`browser-agent: attached...`, and the two
warnings) never reach `surya-headed.log`, which carries only `tracing` output, so
the client side is invisible from here. Someone should run this with the app's
stdout captured before picking a fix.

The browser pane was never opened in this session, so this happens on an ordinary
chat-only run. Worth checking whether it is also why agent CDP has been unreliable.
